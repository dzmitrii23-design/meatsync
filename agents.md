# ORCHESTRATION RULES (V2: Ultra-Secure)

Этот файл содержит железобетонные правила для всех агентов, работающих с данным проектом.

## 1. Test-Driven Development (TDD / Tests First)
Любой создаваемый код или сложная бизнес-логика ОБЯЗАНЫ сопровождаться Unit-тестами или сценариями проверки. Не принимать PR/коммиты без тестов.

## 2. Логическая неизменность (Immutability)
ПЕРЕД любым изменением существующей бизнес-логики агент ОБЯЗАН выдать "Current Logic Summary" и дождаться команды подтверждения.

## 3. Запрет на случайные фиксы (No Random Fixes)
При падении билда, тестов или линтера запрещено подставлять "случайные" решения. Агент обязан провести RCA (Root Cause Analysis), понять корневую причину (система, версия, логика) и предложить осознанное решение.

## 4. Регламент логирования и коммитов (Logging & Commits Protocol)
1. **Запись в логи только по запросу:** Обновление файлов фиксации сессий (`PROJECT_LOG.md` и `SESSION_HISTORY.md`) выполняется **строго и только после команды от пользователя**.
2. **Язык коммитов:** Текст сообщения коммита Git / GitHub пишутся **исключительно на русском языке**.
3. **Строгая последовательность:**
   - **Шаг 1:** Сначала делается запись в файлы фиксации сессии (`PROJECT_LOG.md` / `SESSION_HISTORY.md`).
   - **Шаг 2:** И только затем выполняется коммит на Git / GitHub.

## 5. Регламент уточнения требований (Clarification First — по 1 вопросу)
ПЕРЕД началом реализации любой новой задачи или фичи агент ОБЯЗАН провести анализ крайних случаев и неполноты условий. Если какие-либо требования не определены до конца, агент ОБЯЗАН задавать уточняющие вопросы **СТРОГО ПО ОДНОМУ ВОПРОСУ ЗА РАЗ** (дожидаясь ответа на текущий вопрос перед заданием следующего), чтобы итоговый результат получался с первого раза без переделок.

## 6. Предотвращение ссылочных мутаций и правила отладки
* **Иммутабельность по умолчанию (Immutable by default):** Любое слияние данных из разных источников (клиент, сервер, облако) должно выполняться строго с клонированием объектов (например, через `.map(x => ({ ...x }))` или `structuredClone()`), чтобы избежать случайной мутации ссылок в оперативной памяти Node.js/React.
* **Интеграционное тестирование:** При тестировании синхронизации тесты должны проверять полную цепочку (Data Flow): от симуляции изменения поля на клиенте до детекции разницы и проверки отправки (upsert) на сервер.
* **Рантайм-диагностика:** В случае сбоев синхронизации запрещено полагаться только на теоретические выводы. ИИ-Агент обязан запускать точечные диагностические скрипты для проверки фактического состояния данных в файлах на диске и в облаке.
